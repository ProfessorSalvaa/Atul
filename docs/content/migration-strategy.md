# Migration Strategy

## What was migrated for M2.75

The M2.5 static `sample-data` fixtures (`src/lib/sample-data/courses.ts`)
— 8 courses, 10 modules, 21 lessons — were migrated into the content
engine as the reference implementation. This serves two purposes: it
proves the engine actually works end-to-end (schema → loader → pages →
build), and it's a concrete template for any future bulk migration or
AI-generation batch to follow the same shape.

The migration is a one-time script, kept (not deleted) at
`scripts/migrate-sample-data.mts` as a record and as a template — it
is **not** meant to be re-run; running it again would overwrite any
manual edits made to the migrated content since.

## What the script did

1. Read `SAMPLE_COURSES` directly out of the old TypeScript fixture file
   (via Node's `--experimental-strip-types`, no build step needed).
2. Derived taxonomy (`content/taxonomy/*.yaml`) from the union of tags
   used across all 8 courses, plus a small hand-curated skills/
   career-paths/categories mapping per course (the old fixtures didn't
   have this level of structure — it was added during migration since
   the new schema requires it).
3. Wrote `course.yaml`, `index.mdx`, and `reviews.json` per course.
4. Wrote `module.yaml` per module, `lesson.mdx`/`lesson.yaml` +
   `quiz.json` (+ `flashcards.json` where relevant) per lesson.
5. Generated lesson body prose programmatically (templated on the
   lesson's title/type/course, not hand-written per lesson) — this is
   an honest limitation, called out below, not hidden.

## Known limitation, stated plainly

Lesson prose generated by the migration script is templated, not
individually hand-crafted — it reads coherently and is type-appropriate
(a "code" lesson gets a code example and a code-reading framing; a
"flashcards" lesson gets an embedded `<Flashcard>`), but it is
generic relative to what a human author would write knowing the actual
lesson content. This was a deliberate scope decision: the founder's
explicit instruction was "build the engine, not generate content" and
"do not generate 500 courses" — spending migration effort hand-authoring
21 lessons' worth of bespoke prose would have been content work, not
engine work. The 8 migrated courses exist to prove the pipeline, not to
be the final version of that content; replacing the templated prose with
real authored content is expected before these specific 8 courses are
considered done, and is tracked as follow-up rather than done silently
under the M2.75 banner.

## Strategy for future migrations / bulk imports

The same shape generalizes:

1. Write (or generate) content into a staging location first — never
   directly into `content/courses/` for anything beyond a few files.
2. Run `pnpm content:validate` against the staged batch before moving
   anything live — schema and referential-integrity errors surface
   before a human reviews a single file.
3. Move validated content into place, `status: draft`.
4. Proceed through the normal pipeline
   (`publishing-workflow.md`).

For a hypothetical future migration off a real CMS or database (post-M5,
once a real backend exists), the same content schema
(`src/lib/content/schema/`) becomes the export target — a database-to-
content-files exporter is a natural mirror of this migration script, not
a new architecture.
